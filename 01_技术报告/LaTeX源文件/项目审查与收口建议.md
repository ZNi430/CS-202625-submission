# 当前项目审查与收口建议

## 结论

当前项目的基本架构可以保留，不建议在提交前更换 FastAPI、React、离散事件仿真或现有优化器体系。代码已经形成“输入校验、排产搜索、全流程仿真、指标输出、Web 展示、故障重排”的闭环。现在最重要的不是扩展框架，而是把约束口径、算法名称、实验数据和演示证据统一起来。

## 提交前必须处理

### 已处理：有限缓存可行性筛选与坡口工作站重复计数

已修复同一坡口料框被“坡口加工区间”和“等待转运区间”重复计数的问题；同一料框现在只记录一次完整占用区间。统一目标函数同时对缓存超容量和死锁方案施加强惩罚，最终选解优先从完全可行候选中产生。当前两条优化轨道的缓存峰值均不超过100%，死锁为0。

### 已处理：DQN 名称与实际运行状态统一

当前提交目录没有 `dqn_machine_model.pt`、对应元数据或 PyTorch 运行依赖。程序会自动退回启发式机器分配种子，NSGA-II 仍可运行，但不能据此宣称最终实验已经使用训练后的 DQN。

正式报告、后端名称和前端选项已统一改为“NSGA-II（可选DQN种子）”，将DQN列为扩展模块；除非后续补齐权重、元数据和复现说明，否则不宣称当前实验启用了DQN。

### P0 所有实验必须在 B01 至 B05 修复后重新生成

仓库中 9 月 4 日保存的结果与当前代码已经不完全一致。当前代码复算的 FIFO 指标与旧结果不同，说明不能继续引用旧报告中的 60.09 h、11.79 h 等数值。正式报告、CSV、PNG、截图和视频必须来自同一版本、同一输入、同一随机种子。

### P0 参考 Word 报告不能直接提交

参考稿引用了当前仓库不存在的 `backend/dynamic_rescheduler.py`、`提交材料/仿真结果` 和一组未找到原始产物的 DQN+NSGA-II 实验结果。动态插单部分还描述了“上传新增附件、staging/current 原子提交”等当前代码未实现的完整流程。正式 LaTeX 稿已删去这些未经代码验证的表述。

## 建议尽量处理

### P1 紧急插单目前只是已有任务前移

`rush_order` 接收当前数据集中的钢板名称并将其放到剩余序列前部，尚不能导入一份全新订单并合并零件主数据。若不补功能，演示和报告应称为“紧急任务优先调整”，不要称为完整新增订单插单。

### P1 动态故障对在制钢板采用重新排入而非断点续作

故障时已经在故障机台上加工但尚未完成的钢板，会进入剩余任务并在故障窗口后重新排程。当前版本没有记录已完成加工比例，因此不应在报告中声称支持在制钢板 `finish/interrupt` 双策略。

### P1 Monte Carlo 默认设备数量与题目不一致

`/api/monte_carlo/{run_id}` 在请求未携带设备参数时仍会把 `cutting_machines` 设为 3，从而引入 N8。正式题目场景只有 N2/N5 两台切割机，建议把默认值固定为 2，除非界面明确选择扩展设备情景。

### P1 README 与实际代码口径不一致

README 仍写有旧的 0.48/0.37/0.15 目标权重、已经不存在的流程回放组件和过时目录说明。应统一为当前 `ModelConfig`、当前前端标签和实际存在的文件。

### P1 当前“真实进度轮询”并未在计算中取得 run_id

前端只有在 `/api/run` 返回后才得到 `run_id`，因此计算过程中无法用它查询 `/api/run/progress/{run_id}`。当前界面显示的是诚实标注的预计阶段，真实后端进度只会在结束后查询。该问题不影响算法结果，但报告不要把它描述为实时精确进度。
